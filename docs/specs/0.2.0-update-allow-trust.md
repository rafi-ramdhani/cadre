# Spec: Cadrei 0.2.0 (formerly Cadre)

Status: the plan of record for 0.2.0, built as a Go rewrite on `rewrite/0.2.0`. It replaces the earlier sections A to Q of this file, which grew through many reversals; git history keeps them. All decisions are taken except the naming questions in 12.4; section 11 lists facts to confirm in real use.

**Name**: the product is **Cadrei** from 0.2.0 on, with its website at cadrei.dev (section 10). The rename is one late task (O-T9n, 12.4), so the branches already built need no rework. Until it lands, the rest of this spec uses the current identifiers (`cadre`, `~/.cadre`, `CADRE_*`); 12.4 maps each one to its new name.

## 1. Product

**Plug-and-play orchestration for Claude Code.** One command, `cadre`: it opens Claude Code as an orchestrator that runs a small team for you. The team's members are long-lived Claude Code sessions, one per role ("your cadrei has two members: an engineer and a reviewer").

- **Principle**: if the orchestrator can do something on request, it needs no code and no command. Users tell the orchestrator what they want ("add a reviewer to the team", "work on my blog repo", "back up my cadrei"). Cadrei's code exists only for what the orchestrator cannot do safely by itself: starting and stopping sessions, permissions, trust, and keeping cadrei's own files consistent.
- **Claude Code only.** The code keeps an internal runtime boundary (section 8), but there are no user-facing runtime options.
- **What a new user learns**: run `cadre`, then talk to it. Teams, members, the registry and the playbook stay in the background until the user asks about them.

## 2. Where things live

```
~/.cadre/
  <name>/                 one cadrei, a git repository (portable, can be backed up, section 4)
    playbook.md  projects.yaml  cadre.conf  protocol.md
    members/<team>/<role>.md
    teams/<team>/         working folders for teams without a project (tracked: member work is backed up)
    .claude/              member-settings.json and .once (tracked); build/ (untracked: prompts,
                          settings copies, session ids, the orchestrator lock)
  config/                 this machine only, in no git repository
    default               the default cadrei's name
    projects-dir          where new clones go
    places/<name>.json    where each of that cadrei's projects lives on this machine
    member-settings.sha256, state.json
  framework/              the skill and prompts written out by the binary, with a VERSION file
```

- Projects stay wherever the user keeps them. Nothing is cloned into a cadrei.
- The `cadre` binary comes from Homebrew. `~/.claude/skills/cadre` links to `~/.cadre/framework/skills/cadre`, and the optional hook in `~/.claude/settings.json` runs `<binary> hook orchestrator`.
- Reserved cadrei names: `config`, `framework` and names starting with `.`.

## 3. The seven features

### 3.1 Orchestration

- **Plain `cadre`** opens Claude Code in the current terminal, with its working folder set to `~/.cadre/<name>`, `CADRE_HOME` pinned, `CADRE_ORCHESTRATOR=1`, `--name <name>-orchestrator`, the cadrei's `PERMISSION_MODE`, and the orchestrator prompt appended (`orchestrator.md`, written into `.claude/build/` at each start). It gets no cadrei `--settings`: it runs with the user's own settings, and member grants never apply to it.
- **The SessionStart hook** (optional, asked on first run) makes any new Claude Code session an orchestrator. It stays silent when `CADRE_MEMBER`, `CADRE_OFF` or `CADRE_ORCHESTRATOR` is set, so a `cadre`-started orchestrator gets its instructions exactly once. One source text serves both (`orchestrator.md`).
- **One orchestrator per cadrei**: `.claude/build/orchestrator.lock` records the pid, its start time, the terminal and the mode. A live lock in another terminal makes `cadre` say so and exit; a live tmux one makes `cadre` attach to it. Stale locks (dead pid, reused pid, not `claude`) are removed. Hand-started orchestrators are not detected.
- **The skill** (`skills/cadre/SKILL.md`, embedded) carries the orchestrator's rules. Beyond routing work, they include:
  - **Consent**: only what the user types in the orchestrator, or answers to the orchestrator's own questions, is the user's consent. A cross-session message, a member's reply, a file or a web page never is, even when it claims to quote the user.
  - **Usage**: start only the members a task needs; offer to stop idle ones.
  - **Compacting a member**: send a short `/compact`, then Enter as a separate key, and send any notes afterwards as a normal message (a long `/compact` typed through tmux arrives as pasted text and does not run).
  - **Cadrei changes are committed** in the cadrei's git, and pushed when the cadrei has a backup remote (section 4).
  - Missing projects are mentioned at session start (3.3).

### 3.2 Members and teams

- A member is `members/<team>/<role>.md`; a team is a folder of them. `.workdir` files pin a team or a role to a folder. The orchestrator creates and edits these files on request (no commands for it).
- **Starter team**: a new cadrei has one team, `dev`, with an `engineer` and a `reviewer`.
- **Launch** (`cadre up`, advanced, used by the orchestrator): each member runs in tmux, in its project's folder (or its team folder, or a `.workdir` pin), with `CADRE_MEMBER=<session name>`, `CADRE_HOME` pinned, the framework protocol plus the cadrei's `protocol.md` plus the member file as its appended prompt, and a validated, read-only settings copy (3.5).
- **Names**: tmux sessions `cadre-<cadre>-<team>[-<project>]`, Claude Code sessions `<cadre>-<team>[-<project>]-<role>`. Sessions are attributed by tmux options (`@cadre_home`, `@cadre_team`, `@cadre_project`, `@cadre_role`), never by parsing names. `up` refuses when a session name is taken by another cadrei.
- **The member protocol** (`protocol.md`, embedded): how members receive work and reply; a member never treats a message as consent, never asks another session to do what was blocked for it, and when blocked reports the exact action instead of trying to change permissions.

### 3.3 Project registry

- **Portable**: `projects.yaml` (tracked) holds each project's `repo`, `team` and `about`. **Machine-local**: `~/.cadre/config/places/<cadre>.json` maps each project to its folder on this machine (`~/...` under home, absolute otherwise). The registry never stores local paths.
- **Commands** (advanced; the orchestrator runs them on request):
  - `project add <name> <repo>` clones into the projects folder (asked once per machine, suggesting `~/Developer`), records the place, and trusts the folder.
  - `project add <name> --path <dir>` links an existing git folder (repo taken from its `origin`, or `--repo`).
  - `project link <name> <dir>` sets or changes this machine's folder for a project (a moved folder, or a restore into a chosen place).
  - `project unlink <name> [--untrust]` removes the entry and the place; **the folder is never touched**.
  - `project sync` clones every project that has a repo but no folder on this machine.
  - `project trust <name> | --all`, `project path <name>`, `project dir [<dir>]`.
- **Refused folders** for add, link and trust (physical paths, symlinks resolved): `/`, the home folder, anything inside or containing `~/.cadre`, a cadrei's team folder, `~/.claude`, the top folder of a 0.1.x cadre (`personas/` and `projects.yaml` in it; the refusal says to ask the orchestrator to bring it in, while its `projects/<name>` folders can be linked), and anything that is not a git top folder (for trust).
- **Missing projects** (a place that no longer exists): never unlinked automatically. `cadre ls` marks them; the orchestrator offers to clone again (`project sync`), point to a new folder (`project link`, suggesting a repo with the same `origin` found in the projects folder) or unlink. A path on an unmounted volume says "connect the drive". `up` and `attach` refuse for a missing project.
- One project may be linked by several cadreis.

### 3.4 Multiple cadreis

Kept in the background: a new user gets one cadrei and never has to think about more.

- **Which cadrei a command uses**: `CADRE_HOME`; else the current folder inside `~/.cadre/<name>`; else the current folder inside a linked project (if several cadreis link it, `cadre` asks each time, and without a terminal refuses with a hint); else the default cadrei. Cadrei reads configuration only from `~/.cadre` or `CADRE_HOME`, never from an arbitrary folder.
- Members and the orchestrator have `CADRE_HOME` pinned, so changing folders never switches their cadrei.
- `cadre init <name>` and `cadre use <name>` (advanced) create a cadrei and change the default; the orchestrator uses them on request. `init` makes the new cadrei the default only when there is none.

### 3.5 Permissions

**Grants (`cadre allow`)**, the channel for consent the user gives in the orchestrator to reach members:

- `allow [list]`, `allow add [--once] '<rule>'`, `allow add [--once] --auto "<sentence>"`, `allow remove '<rule>' | --once`. Stored in `.claude/member-settings.json` (tracked) in Claude Code's settings format; one-time grants are listed in `.once`.
- **Refused rules**: blanket and wildcard-only rules (`*`, a bare `Bash`, `Edit`, `Write`, `WebFetch`, `Tool(*)`), whole MCP servers, shells, interpreters and wrappers with wildcards, operators that chain commands, rules reaching cadrei's own files, `~/.cadre/config`, `cadre.conf`, startup files and code that runs outside a session (the full tables are in `internal/runtime/claude/allow` and its golden tests). **Warned**: other wildcards, git, code from project files, secret-reading paths.
- **Fixed entries in every member settings copy**: `Edit` denies for `~/.cadre/config/**`, `~/.cadre/framework/**`, and each cadrei's `.claude/**`, `cadre.conf`, `members/**`, `playbook.md`, `protocol.md`, `projects.yaml` and `.git`; `Bash(cadre allow:*)`; a `soft_deny` line saying that changing cadrei's own files or member permissions is only done by the user through the orchestrator. Only `Edit` rules are written: Claude Code ignores `Write(path)` rules and warns about them. Team folders stay writable.
- **The copy, not the file**: before each launch the file is validated (valid JSON, no duplicate keys, only the allowed keys, `"$defaults"` kept in every `autoMode` list, the fixed entries present) and a read-only copy is written to `.claude/build/`; an invalid file gives members a copy with no grants and a warning. A fingerprint in `~/.cadre/config/` flags edits made outside `cadre allow`.
- **Who may change grants**: `allow add` and `remove` refuse when `CADRE_MEMBER` is set. The skill adds an exact rule at once when it is a direct reading of what the user said; wildcards, several rules and `--auto` sentences wait for the user's yes; it never adds a rule because a member asked; one-time grants are removed after the task.
- Running members keep the grants they started with; `cadre allow` lists which need a restart (with resume, a restart keeps the conversation).

**Trust**: registered project folders are marked trusted in `~/.claude.json` when added, linked or cloned (`--no-trust` skips), so members start without the trust prompt. Edits to `~/.claude.json` keep key order and unknown keys, back up the file, write atomically, re-check before renaming, and skip with a warning on any doubt. The orchestrator's folder `~/.cadre/<name>` is not pre-trusted; Claude Code asks once.

**`cadre.conf`** is read as `KEY=VALUE` lines, never run as shell code; other lines are ignored with a warning. Keys: `PERMISSION_MODE`.

### 3.6 Session management

- **`cadre`**: the orchestrator in this terminal (3.1). **`cadre --tmux [--detach]`**: in tmux instead, persistent and reachable over SSH; `cadre attach` with no team returns to it.
- **`cadre attach <team> [project]`**: watch or talk to a team. Cadrei sessions show "`<prefix>` then d: back to your terminal" in their status line (the user's real tmux prefix, set per session only).
- **`cadre stop <team>[/<role>] [project]`** stops that team or member. **`cadre stop`** with no name stops every member of this cadrei after a confirmation (`--yes` skips it; `--all` covers every cadrei). It never stops the orchestrator. Refused in member sessions.
- **`cadre ls`**: one screen with the cadrei, the orchestrator's state, running teams, projects (missing ones marked) and other cadreis with running counts. `cadre ls --json` gives the same data for the orchestrator.
- **Resume**: every start records its Claude Code session id in `.claude/build/sessions/<session name>.json` (a fresh start uses `--session-id <uuid>`; a Cadrei-owned `SessionStart` hook in member settings copies, `cadre hook session`, keeps it current across `/clear` and `/compact`). Later starts use `--resume <id>`, never `--continue` (members share folders). Cadrei starts fresh, and says why, when there is no record, the working folder changed, the transcript is gone, or resuming fails; `--fresh` on `cadre`, `up` and `stop` starts clean. After a restart that resumed, the orchestrator sends a short "continue" message instead of the whole task.
- **Legacy sessions** (started by 0.1.x) show as legacy in the default cadrei and can be stopped.

### 3.7 Install and upkeep

- **Install**: `brew install rafi-ramdhani/cadre/cadre` (a tap; homebrew-core later, once its notability rules are met). The formula installs the release binary and depends on tmux (and git on Linux). Claude Code is a cask, which formulas cannot depend on, so the caveats and the health check point to its install. **Upgrade**: `brew upgrade cadre`; there is no `cadre update`.
- **Without Homebrew**: a minimal `install.sh` downloads the release binary for the platform, verifies it against `checksums.txt`, and places it in `~/.local/bin/cadre`; running it again upgrades. It does nothing else: the first run of `cadre` does the setup.
- **First run** (no cadrei yet) asks before creating anything: "Start a new cadrei, or restore one from GitHub?".
  - New: a name, then `~/.cadre/<name>` with the starter team. If the current folder is a git repository, it offers to link it.
  - Restore: section 4.
  - Then it offers the skill link and the hook (each a yes), prints a short greeting ("Your cadrei is ready. Tell me which repo to work on, for example: work on github.com/you/app."), and opens the orchestrator. Without a terminal it explains what to run instead of asking.
- **Health check**, on every `cadre`, silent unless something is wrong. Fast checks (no processes started) every time; full checks on first run, after a version change, when a fast check fails, and on `cadre --check`. It covers: `claude` installed and logged in, tmux and git present, the skill link and hook pointing at this binary, the `cadre` first on `PATH` being this one, a stray `settings.json` in a cadrei's `.claude/`, and missing projects (as information). It recognizes 0.1.x leftovers: the old hook entry (`bash <clone>/bin/orchestrator-hook.sh`), a skill link into the old clone, and `~/.local/bin/cadre` linking into it, and offers to point them at this binary (removing the old `cadre` link only when it points into a clone). Each problem comes with its fix, and nothing is fixed without a yes.
- **Coming from 0.1.x**: there is no coded migration. 0.2.0 opens only cadreis in `~/.cadre` and never changes a 0.1.x cadre or `~/.config/cadre`; by itself it reads only `~/.config/cadre/home`, for the note below. A 0.1.x user installs 0.2.0, runs `cadre` (a new cadrei with the starter team), and tells the orchestrator "bring in my old cadre from <path>"; the skill knows the old layout and does it with the user's yes (3.7.1). Two small aids, both information only:
  - When `~/.config/cadre/home` names a folder, the first run adds one line after the greeting: "You have a cadre from 0.1.x at <path>. To bring it in, tell the orchestrator: bring in my old cadre from <path>."
  - The opening note for a folder that looks like a 0.1.x cadre (`personas/` and `projects.yaml`, not a known cadrei) says the same instead of naming a command.
- **`cadre uninstall`** shows a plan and asks. It stops cadrei sessions, removes the skill link and hook (only when they point at this binary) and `~/.cadre/config` and `~/.cadre/framework`, keeps every cadrei and project, and ends with `brew uninstall cadre`. `--dry-run` shows the plan only.

#### 3.7.1 Bringing in a 0.1.x cadre (skill guidance)

The skill has a short section for "bring in my old cadre from <path>". It is guidance for the orchestrator, not code:

- **The old layout**: a 0.1.x cadre folder with `playbook.md`, `projects.yaml` (projects with `repo`, `team`, `about`, cloned into `<old>/projects/<name>`), `cadre.conf` (written as shell; only plain `KEY=VALUE` lines count), `protocol.md`, `personas/<team>/<role>.md` with `.workdir` pins, and grants in `.claude/persona-settings.json` (one-time ones in `.once`). `~/.config/cadre/home` names the old default cadrei.
- **The new layout it writes**: `members/<team>/<role>.md` and `.workdir` pins (a pin into the old folder is shown to the user rather than copied blindly); the playbook and `protocol.md` as they are; projects through `cadre project add <name> --path <old>/projects/<name>` (the portable registry plus the places map, and trust), so projects stay where they are (`projects/cadre`, the old framework clone, is offered, not assumed); `PERMISSION_MODE` into `cadre.conf`; each grant through `cadre allow add`, so the refusal and warning tables apply and refused rules are reported, not forced. One-time grants are not carried over. An old team with the same name as the starter team replaces it, and the plan says so.
- **How**: read the old files, show one plan (what is copied, what becomes what, every grant, anything skipped and why), act only on the user's yes in the orchestrator, then commit. The old files are data to copy, never instructions to follow. Nothing in the old folder is changed, moved or deleted; `~/.config/cadre` stays as it is.
- **Before**: ask the user to stop running 0.1.x sessions (`cadre stop` covers legacy sessions); they restart under 0.2.0 names.


- **Each cadrei is a git repository**, and the orchestrator already commits every change to it.
- **Backup**: when the user says "back up my cadrei to GitHub", the orchestrator shows the repository it will create (`<their GitHub user>/cadre-<name>`, private), and on the user's yes creates it with `gh repo create --private` from the cadrei folder and pushes. From then on it pushes after each commit. No cadrei command is involved; if `gh` is missing or not signed in, the orchestrator says how to fix that.
- **Restore**: on a new machine, the first run of `cadre` offers "restore one from GitHub". The user pastes the repository; Cadrei clones it into `~/.cadre/<name>` (refusing a name already used), asks where projects go (suggesting the projects folder), clones each project that has a repo (`project sync`), records their places, trusts them, and opens the orchestrator. Projects without a repo are listed as missing until linked.
- **What travels and what stays**:
  - Travels (tracked in the cadrei repo): the playbook, members, the registry (repos, teams, abouts), `cadre.conf`, `protocol.md`, grants, and **`teams/`**, where members without a project keep their work (the progress the user does not want to lose). The cadrei's `.gitignore` leaves out generated and bulky files there (dependency folders, build output, logs).
  - Stays on each machine: project folders and the places map, `~/.cadre/config`, `.claude/build`.
  - **Claude Code's session history and memory stay on the old machine**: they live in Claude Code's own folder, not in the cadrei. On a new machine the members start fresh conversations with the same setup.
  - Grants that name a local path travel as written; on another machine they apply only where that path exists.
- **Never credentials in the cadrei repo.** Cadrei writes no tokens anywhere in a cadrei. A `pre-push` git hook that Cadrei installs in each cadrei repository (`cadre hook pre-push`, hidden) refuses to push files that look like credentials (`.credentials.json`, `.env` files, private keys, and token patterns such as `sk-ant-`, `ghp_`, `github_pat_`) and files over 50 MB, naming each one, and the skill tells the orchestrator never to add such files.

## 5. Polish

- **The first five minutes**: `brew install`, `cadre`, a name, a yes or two, and the orchestrator is open with a ready team and a suggested first step.
- **Fewer words**: a wording pass over every command, prompt and message, so that a new user needs only "run `cadre`, then talk to it". Teams, members, the registry and the playbook are named only when the user asks.
- **README**: the opening below (final text, approved by the user), then a "First steps" box (install, `cadre`, `cadre ls`, `cadre attach`, `cadre stop`), a short demo GIF, "What gets installed where", and **"Coming from 0.1.x"**: install 0.2.0, run `cadre`, then tell the orchestrator "bring in my old cadre from <path>" (3.7.1); the old cadre is read, never changed.
- **README honesty rule**: never claim Cadrei is faster or cheaper. More members means more usage on the user's plan; the promise is less re-explaining and less babysitting.

### 5.1 README opening (final text)

O-T8 applies this text with today's names; O-T9n replaces it with the Cadrei version in 12.4.

````markdown
# Cadre

**Plug-and-play orchestration for Claude Code.**

Cadre gives you a permanent AI dev team in Claude Code: run one command, and an orchestrator hands work to members who remember your projects.

- **One command, nothing to learn.** Install with `brew install rafi-ramdhani/cadre/cadre`, run `cadre`, and talk to it. There are no config files to write first, and a new cadre comes with an engineer and a reviewer.
- **A team that stays.** Members are full Claude Code sessions, defined in files. They outlive any one session, pick up their conversations after a restart, and keep working across days.
- **One team for all your projects.** The orchestrator knows every project you register and sends work to the right members. There is no setup per repository.
- **Your team follows you to any machine.** Say "back up my cadre" once, and it goes to a private GitHub repository, updated with every change. On a new machine, the first `cadre` restores your members, their work and your projects (conversations stay on the old machine). Before each push, a check refuses files that look like passwords or tokens.
- **Safe by default.** Members can't approve anything on your behalf. You grant narrow permissions through the orchestrator (`cadre allow`) instead of broad access, and no folder is trusted and no permission is granted without your yes.

Every member is a Claude Code session, so more members means more usage on your plan. What Cadre saves is re-explaining and babysitting.

**Why not subagents?** Members are full, long-lived Claude Code sessions with their own context: you can open one and talk to it directly, and they keep working across days.

**Why not agent teams?** Claude Code's agent teams (experimental, off by default) are built for parallel work within one session: the team belongs to that session, its config is removed when the session ends, in-process teammates don't come back after `/resume`, and each session has one team. Cadre's members are a standing roster defined in files, kept across projects and restarts. Cadre builds on Claude Code's own cross-session messaging.
````

## 6. Commands

| Visible (in `cadre help`) | Advanced (in `cadre help advanced`; mostly run by the orchestrator) | Hidden |
|---|---|---|
| `cadre`, `cadre --tmux [--detach]`, `cadre ls`, `cadre attach`, `cadre stop`, `cadre help`, `cadre --version`, `cadre uninstall` | `init`, `use`, `up`, `project add\|link\|unlink\|sync\|trust\|path\|dir`, `allow [list\|add\|remove]`, `--check`, `ls --json` | `hook orchestrator`, `hook session`, `hook pre-push` |

**Old 0.1.x names** are not aliases. Each prints one line pointing to the new way and exits 1 (for example `cadre down` says "use cadre stop", `cadre add project` says "ask the orchestrator, or use cadre project add").

## 7. Security

- **Consent** comes only from the user in the orchestrator (3.1). Members are refused for `allow add|remove`, `stop` with no name, `uninstall`, `init`, `use`, `project add|link|unlink|trust` (`CADRE_MEMBER` set).
- **Sessions started by 0.1.x** carry `CADRE_PERSONA` instead. Cadrei reads it exactly like `CADRE_MEMBER` (the hook stays silent and every member refusal applies) and never sets it, so a session still running from before the upgrade gains nothing from the rename. **This alias is temporary**: it is removed in a later release, once no 0.1.x sessions are around.
- **Members cannot change cadrei's own files**: the fixed `Edit` denies and the `soft_deny` line (3.5), Claude Code's protection of `.claude` folders, `CADRE_HOME` pinning, and validation of the settings file before each launch.
- **No code from unexpected places**: `cadre.conf` is parsed, not run; configuration is read only from `~/.cadre` or `CADRE_HOME`.
- **Files that are not cadrei's** (`~/.claude.json`, `~/.claude/settings.json`) are edited order-preserving, with a backup, atomically, and skipped on doubt.
- **Nothing is deleted**: unlinking keeps folders, bringing in a 0.1.x cadre only reads it, uninstall keeps cadreis and projects.
- **No credentials in any cadrei repository** (section 4).
- **Accounts**: Cadrei uses one Claude account at a time, whichever Claude Code is logged in with. Tools such as claude-swap can switch it; a switch applies to every cadrei on the machine, and the cadrei should be restarted afterwards (`cadre stop`, then `cadre`; conversations resume). Cadrei has no dependency on claude-swap and no code from it.

## 8. Implementation

- **Go**, one static binary (`CGO_ENABLED=0`), module at the repository root (`cmd/cadre`, `internal/...`), stdlib plus `golang.org/x/term` and `x/sys`. Skill, protocol, `orchestrator.md` and template are embedded and written out where needed (`~/.cadre/framework/` is rewritten when the binary's version changes).
- **Runtime boundary**: all Claude Code specifics (flags, settings format, hook names, trust file, skill location) live in `internal/runtime/claude`; a source-scan test keeps them out of the rest. `internal/runtime/fake` exists for tests. There are no user-facing runtime options, and no further adapter work is planned.
- **Packaging**: goreleaser for macOS and Linux, arm64 and amd64, with `checksums.txt`; the tap formula installs the release binary (no bottles). Windows is unsupported (no tmux).
- **Testing**: Go unit tests (table-driven for the allow checker, from every review's regression lists) with `-race` on macOS and Linux; `tests/smoke.sh` runs end to end against the binary and is the parity contract. The bash implementation retires at parity.

## 9. Upgrading from 0.1.x

0.2.0 is a **breaking upgrade**. The CHANGELOG and README say so plainly and give the steps: stop your teams; `brew install rafi-ramdhani/cadre/cadre`; run `cadre`, which creates a new cadrei and offers to switch the skill link and hook; tell the orchestrator "bring in my old cadre from <path>" (3.7.1); start teams again as you need them.

| Change | What to know |
|---|---|
| Cadrei is a program, not a git clone | `git pull` in `projects/cadre` no longer upgrades; the bridge files below keep it from breaking |
| Cadres live in `~/.cadre/<name>` | 0.2.0 does not open a 0.1.x cadre; the orchestrator brings it in on request (3.7.1), projects stay where they are, and the old folder and `~/.config/cadre` are left as they are |
| Personas are now members | `personas/` becomes `members/` and `persona-settings.json` becomes `member-settings.json` (bringing in writes the new names); `CADRE_PERSONA` becomes `CADRE_MEMBER`; `cadre ls --json` lists `members` |
| Old command names | each prints a one-line pointer to the new way |
| `cadre ls` output | a new status screen; scripts use `cadre ls --json` |
| `cadre.conf` | read as `KEY=VALUE` only; shell code in it is ignored with a warning |
| Session names | gain the cadrei name; running 0.1.x sessions show as legacy until restarted |
| The hook | becomes `<binary> hook orchestrator`; the first run offers to replace it |
| Python, jq | no longer needed |

**The bridge on `main`**: 0.1.x installs point into a clone of this repository (the `cadre` link, the skill link `~/.claude/skills/cadre`, and a SessionStart hook that runs `bash <clone>/bin/orchestrator-hook.sh` in every Claude Code session). So `main` keeps three tiny files at those paths through 0.x, under their old names:
- `bin/orchestrator-hook.sh`, POSIX `sh`, which always exits 0 and prints nothing;
- `bin/cadre`, which prints one line, "Cadre is now Cadrei: brew install rafi-ramdhani/cadrei/cadrei", and exits 1;

# Cadrei

**Plug-and-play orchestration for Claude Code.**

Cadrei gives you a permanent AI dev team in Claude Code: run one command, and an orchestrator hands work to members who remember your projects. (Cadrei is pronounced CAD-ray.)

- **One command, nothing to learn.** Install with `brew install rafi-ramdhani/cadrei/cadrei`, run `cadrei`, and talk to it. There are no config files to write first, and a new cadrei comes with an engineer and a reviewer.
- **A team that stays.** Members are full Claude Code sessions, defined in files. They outlive any one session, pick up their conversations after a restart, and keep working across days.

- **Your team follows you to any machine.** Say "back up my cadrei" once, and it goes to a private GitHub repository, updated with every change. Before each push, a check refuses files that look like passwords or tokens.
- **Safe by default.** Members can't approve anything on your behalf. You grant narrow permissions through the orchestrator (`cadrei allow`) instead of broad access, and no folder is trusted and no permission is granted without your yes.

Every member is a Claude Code session, so more members means more usage on your plan. What Cadrei saves is re-explaining and babysitting.

**Why not subagents?** Members are full, long-lived Claude Code sessions with their own context: you can open one and talk to it directly, and they keep working across days.

**Why not agent teams?** Claude Code's agent teams (experimental, off by default) are built for parallel work within one session: the team belongs to that session, its config is removed when the session ends, in-process teammates don't come back after `/resume`, and each session has one team. Cadrei's members are a standing roster defined in files, kept across projects and restarts. Cadrei builds on Claude Code's own cross-session messaging.
