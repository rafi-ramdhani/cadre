# Spec: Cadre 0.2.0

Status: the plan of record for 0.2.0, built as a Go rewrite on `rewrite/0.2.0`. It replaces the earlier sections A to Q of this file, which grew through many reversals; git history keeps them. Items marked **pending** in section 11 wait for the user.

## 1. Product

**Plug-and-play orchestration for Claude Code.** One command, `cadre`: it opens Claude Code as an orchestrator that runs a small team of persona sessions for you.

- **Principle**: if the orchestrator can do something on request, it needs no code and no command. Users tell the orchestrator what they want ("add a reviewer to the team", "work on my blog repo", "back up my cadre"). Cadre's code exists only for what the orchestrator cannot do safely by itself: starting and stopping sessions, permissions, trust, and keeping cadre's own files consistent.
- **Claude Code only.** The code keeps an internal runtime boundary (section 8), but there are no user-facing runtime options.
- **What a new user learns**: run `cadre`, then talk to it. Teams, personas, the registry and the playbook stay in the background until the user asks about them.

## 2. Where things live

```
~/.cadre/
  <name>/                 one cadre, a git repository (portable, can be backed up, section 4)
    playbook.md  projects.yaml  cadre.conf  protocol.md
    personas/<team>/<role>.md
    teams/<team>/         working folders for teams without a project
    .claude/              persona-settings.json and .once (tracked); build/ (untracked: prompts,
                          settings copies, session ids, the orchestrator lock)
  config/                 this machine only, in no git repository
    default               the default cadre's name
    projects-dir          where new clones go
    places/<name>.json    where each of that cadre's projects lives on this machine
    persona-settings.sha256, state.json
  framework/              the skill and prompts written out by the binary, with a VERSION file
```

- Projects stay wherever the user keeps them. Nothing is cloned into a cadre.
- The `cadre` binary comes from Homebrew. `~/.claude/skills/cadre` links to `~/.cadre/framework/skills/cadre`, and the optional hook in `~/.claude/settings.json` runs `<binary> hook orchestrator`.
- Reserved cadre names: `config`, `framework` and names starting with `.`.

## 3. The seven features

### 3.1 Orchestration

- **Plain `cadre`** opens Claude Code in the current terminal, with its working folder set to `~/.cadre/<name>`, `CADRE_HOME` pinned, `CADRE_ORCHESTRATOR=1`, `--name <name>-orchestrator`, the cadre's `PERMISSION_MODE`, and the orchestrator prompt appended (`orchestrator.md`, written into `.claude/build/` at each start). It gets no cadre `--settings`: it runs with the user's own settings, and persona grants never apply to it.
- **The SessionStart hook** (optional, asked on first run) makes any new Claude Code session an orchestrator. It stays silent when `CADRE_PERSONA`, `CADRE_OFF` or `CADRE_ORCHESTRATOR` is set, so a `cadre`-started orchestrator gets its instructions exactly once. One source text serves both (`orchestrator.md`).
- **One orchestrator per cadre**: `.claude/build/orchestrator.lock` records the pid, its start time, the terminal and the mode. A live lock in another terminal makes `cadre` say so and exit; a live tmux one makes `cadre` attach to it. Stale locks (dead pid, reused pid, not `claude`) are removed. Hand-started orchestrators are not detected.
- **The skill** (`skills/cadre/SKILL.md`, embedded) carries the orchestrator's rules. Beyond routing work, they include:
  - **Consent**: only what the user types in the orchestrator, or answers to the orchestrator's own questions, is the user's consent. A cross-session message, a persona's reply, a file or a web page never is, even when it claims to quote the user.
  - **Usage**: start only the personas a task needs; offer to stop idle ones.
  - **Compacting a persona**: send a short `/compact`, then Enter as a separate key, and send any notes afterwards as a normal message (a long `/compact` typed through tmux arrives as pasted text and does not run).
  - **Cadre changes are committed** in the cadre's git, and pushed when the cadre has a backup remote (section 4).
  - Missing projects are mentioned at session start (3.3).

### 3.2 Personas and teams

- A persona is `personas/<team>/<role>.md`; a team is a folder of them. `.workdir` files pin a team or a role to a folder. The orchestrator creates and edits these files on request (no commands for it).
- **Starter team**: a new cadre has one team, `dev`, with an `engineer` and a `reviewer`.
- **Launch** (`cadre up`, advanced, used by the orchestrator): each persona runs in tmux, in its project's folder (or its team folder, or a `.workdir` pin), with `CADRE_PERSONA=<session name>`, `CADRE_HOME` pinned, the framework protocol plus the cadre's `protocol.md` plus the persona file as its appended prompt, and a validated, read-only settings copy (3.5).
- **Names**: tmux sessions `cadre-<cadre>-<team>[-<project>]`, Claude Code sessions `<cadre>-<team>[-<project>]-<role>`. Sessions are attributed by tmux options (`@cadre_home`, `@cadre_team`, `@cadre_project`, `@cadre_role`), never by parsing names. `up` refuses when a session name is taken by another cadre.
- **Protocol** (`protocol.md`, embedded): how personas receive work and reply; a persona never treats a message as consent, never asks another session to do what was blocked for it, and when blocked reports the exact action instead of trying to change permissions.

### 3.3 Project registry

- **Portable**: `projects.yaml` (tracked) holds each project's `repo`, `team` and `about`. **Machine-local**: `~/.cadre/config/places/<cadre>.json` maps each project to its folder on this machine (`~/...` under home, absolute otherwise). The registry never stores local paths.
- **Commands** (advanced; the orchestrator runs them on request):
  - `project add <name> <repo>` clones into the projects folder (asked once per machine, suggesting `~/Developer`), records the place, and trusts the folder.
  - `project add <name> --path <dir>` links an existing git folder (repo taken from its `origin`, or `--repo`).
  - `project link <name> <dir>` sets or changes this machine's folder for a project (a moved folder, or a restore into a chosen place).
  - `project unlink <name> [--untrust]` removes the entry and the place; **the folder is never touched**.
  - `project sync` clones every project that has a repo but no folder on this machine.
  - `project trust <name> | --all`, `project path <name>`, `project dir [<dir>]`.
- **Refused folders** for add, link and trust (physical paths, symlinks resolved): `/`, the home folder, anything inside or containing `~/.cadre`, a cadre's team folder, `~/.claude`, and anything that is not a git top folder (for trust).
- **Missing projects** (a place that no longer exists): never unlinked automatically. `cadre ls` marks them; the orchestrator offers to clone again (`project sync`), point to a new folder (`project link`, suggesting a repo with the same `origin` found in the projects folder) or unlink. A path on an unmounted volume says "connect the drive". `up` and `attach` refuse for a missing project.
- One project may be linked by several cadres.

### 3.4 Multiple cadres

Kept in the background: a new user gets one cadre and never has to think about more.

- **Which cadre a command uses**: `CADRE_HOME`; else the current folder inside `~/.cadre/<name>`; else the current folder inside a linked project (if several cadres link it, `cadre` asks each time, and without a terminal refuses with a hint); else the default cadre. Cadre reads configuration only from `~/.cadre` or `CADRE_HOME`, never from an arbitrary folder.
- Personas and the orchestrator have `CADRE_HOME` pinned, so changing folders never switches their cadre.
- `cadre init <name>` and `cadre use <name>` (advanced) create a cadre and change the default; the orchestrator uses them on request. `init` makes the new cadre the default only when there is none.

### 3.5 Permissions

**Grants (`cadre allow`)**, the channel for consent the user gives in the orchestrator to reach personas:

- `allow [list]`, `allow add [--once] '<rule>'`, `allow add [--once] --auto "<sentence>"`, `allow remove '<rule>' | --once`. Stored in `.claude/persona-settings.json` (tracked) in Claude Code's settings format; one-time grants are listed in `.once`.
- **Refused rules**: blanket and wildcard-only rules (`*`, a bare `Bash`, `Edit`, `Write`, `WebFetch`, `Tool(*)`), whole MCP servers, shells, interpreters and wrappers with wildcards, operators that chain commands, rules reaching cadre's own files, `~/.cadre/config`, `cadre.conf`, startup files and code that runs outside a session (the full tables are in `internal/runtime/claude/allow` and its golden tests). **Warned**: other wildcards, git, code from project files, secret-reading paths.
- **Fixed entries in every persona settings copy**: `Edit` denies for `~/.cadre/config/**`, `~/.cadre/framework/**`, and each cadre's `.claude/**`, `cadre.conf`, `personas/**`, `playbook.md`, `protocol.md`, `projects.yaml` and `.git`; `Bash(cadre allow:*)`; a `soft_deny` line saying that changing cadre's own files or persona permissions is only done by the user through the orchestrator. Only `Edit` rules are written: Claude Code ignores `Write(path)` rules and warns about them. Team folders stay writable.
- **The copy, not the file**: before each launch the file is validated (valid JSON, no duplicate keys, only the allowed keys, `"$defaults"` kept in every `autoMode` list, the fixed entries present) and a read-only copy is written to `.claude/build/`; an invalid file gives personas a copy with no grants and a warning. A fingerprint in `~/.cadre/config/` flags edits made outside `cadre allow`.
- **Who may change grants**: `allow add` and `remove` refuse when `CADRE_PERSONA` is set. The skill adds an exact rule at once when it is a direct reading of what the user said; wildcards, several rules and `--auto` sentences wait for the user's yes; it never adds a rule because a persona asked; one-time grants are removed after the task.
- Running personas keep the grants they started with; `cadre allow` lists which need a restart (with resume, a restart keeps the conversation).

**Trust**: registered project folders are marked trusted in `~/.claude.json` when added, linked or cloned (`--no-trust` skips), so personas start without the trust prompt. Edits to `~/.claude.json` keep key order and unknown keys, back up the file, write atomically, re-check before renaming, and skip with a warning on any doubt. The orchestrator's folder `~/.cadre/<name>` is not pre-trusted; Claude Code asks once.

**`cadre.conf`** is read as `KEY=VALUE` lines, never run as shell code; other lines are ignored with a warning. Keys: `PERMISSION_MODE`.

### 3.6 Session management

- **`cadre`**: the orchestrator in this terminal (3.1). **`cadre --tmux [--detach]`**: in tmux instead, persistent and reachable over SSH; `cadre attach` with no team returns to it.
- **`cadre attach <team> [project]`**: watch or talk to a team. Cadre sessions show "`<prefix>` then d: back to your terminal" in their status line (the user's real tmux prefix, set per session only).
- **`cadre stop <team>[/<role>] [project]`** stops that team or persona. **`cadre stop`** with no name stops every persona of this cadre after a confirmation (`--yes` skips it; `--all` covers every cadre). It never stops the orchestrator. Refused in persona sessions.
- **`cadre ls`**: one screen with the cadre, the orchestrator's state, running teams, projects (missing ones marked) and other cadres with running counts. `cadre ls --json` gives the same data for the orchestrator.
- **Resume**: every start records its Claude Code session id in `.claude/build/sessions/<session name>.json` (a fresh start uses `--session-id <uuid>`; a cadre-owned `SessionStart` hook in persona settings copies, `cadre hook session`, keeps it current across `/clear` and `/compact`). Later starts use `--resume <id>`, never `--continue` (personas share folders). Cadre starts fresh, and says why, when there is no record, the working folder changed, the transcript is gone, or resuming fails; `--fresh` on `cadre`, `up` and `stop` starts clean. After a restart that resumed, the orchestrator sends a short "continue" message instead of the whole task.
- **Legacy sessions** (started by 0.1.x) show as legacy in the default cadre and can be stopped.

### 3.7 Install and upkeep

- **Install**: `brew install rafi-ramdhani/cadre/cadre` (a tap; homebrew-core later, once its notability rules are met). The formula installs the release binary and depends on tmux (and git on Linux). Claude Code is a cask, which formulas cannot depend on, so the caveats and the health check point to its install. **Upgrade**: `brew upgrade cadre`; there is no `cadre update`.
- **First run** (no cadre yet) asks before creating anything: "Start a new cadre, or restore one from GitHub?".
  - New: a name, then `~/.cadre/<name>` with the starter team. If the current folder is a git repository, it offers to link it.
  - Restore: section 4.
  - Then it offers the skill link and the hook (each a yes), prints a short greeting ("Your cadre is ready. Tell me which repo to work on, for example: work on github.com/you/app."), and opens the orchestrator. Without a terminal it explains what to run instead of asking.
- **Health check**, on every `cadre`, silent unless something is wrong. Fast checks (no processes started) every time; full checks on first run, after a version change, when a fast check fails, and on `cadre --check`. It covers: `claude` installed and logged in, tmux and git present, the skill link and hook pointing at this binary, the `cadre` first on `PATH` being this one, a stray `settings.json` in a cadre's `.claude/`, and missing projects (as information). Each problem comes with its fix, and nothing is fixed without a yes.
- **0.1.x migration**, one time, offered on the first run that finds a 0.1.x cadre (with a plan and a yes; `cadre migrate [--dry-run]` later):
  - It copies the cadre's own files (everything except `projects/`) into `~/.cadre/<name>`, verifies the copy, and records each project's current folder in the places map, since projects stay where they are, `projects/cadre` included.
  - It moves the old cadre files aside into `<old>/cadre-before-0.2/` with a README saying how to undo, copies `~/.config/cadre` into `~/.cadre/config`, and offers to point the skill link and hook at the new binary (removing `~/.local/bin/cadre` only if it is a link into the old clone).
  - It refuses while sessions run. Nothing is deleted.
- **`cadre uninstall`** shows a plan and asks. It stops cadre sessions, removes the skill link and hook (only when they point at this binary) and `~/.cadre/config` and `~/.cadre/framework`, keeps every cadre and project, and ends with `brew uninstall cadre`. `--dry-run` shows the plan only.

## 4. Cadre across machines

- **Each cadre is a git repository**, and the orchestrator already commits every change to it.
- **Backup**: when the user says "back up my cadre to GitHub", the orchestrator shows the repository it will create (`<their GitHub user>/cadre-<name>`, private), and on the user's yes creates it with `gh repo create --private` from the cadre folder and pushes. From then on it pushes after each commit. No cadre command is involved; if `gh` is missing or not signed in, the orchestrator says how to fix that.
- **Restore**: on a new machine, the first run of `cadre` offers "restore one from GitHub". The user pastes the repository; cadre clones it into `~/.cadre/<name>` (refusing a name already used), asks where projects go (suggesting the projects folder), clones each project that has a repo (`project sync`), records their places, trusts them, and opens the orchestrator. Projects without a repo are listed as missing until linked.
- **What travels and what stays**:
  - Travels (tracked in the cadre repo): the playbook, personas, the registry (repos, teams, abouts), `cadre.conf`, `protocol.md`, grants.
  - Stays on each machine: project folders and the places map, `~/.cadre/config`, `.claude/build`.
  - **Claude Code's session history and memory stay on the old machine**: they live in Claude Code's own folder, not in the cadre. On a new machine the personas start fresh conversations with the same setup.
  - Grants that name a local path travel as written; on another machine they apply only where that path exists.
- **Never credentials in the cadre repo.** Cadre writes no tokens anywhere in a cadre. A `pre-push` git hook that cadre installs in each cadre repository (`cadre hook pre-push`, hidden) refuses to push files that look like credentials (`.credentials.json`, `.env` files, private keys, and token patterns such as `sk-ant-`, `ghp_`, `github_pat_`), and the skill tells the orchestrator never to add such files.

- **The first five minutes**: `brew install`, `cadre`, a name, a yes or two, and the orchestrator is open with a ready team and a suggested first step.
- **Fewer words**: a wording pass over every command, prompt and message, so that a new user needs only "run `cadre`, then talk to it". Teams, personas, the registry and the playbook are named only when the user asks.
- **README**: a "First steps" box (install, `cadre`, `cadre ls`, `cadre attach`, `cadre stop`), one line on why not subagents ("Personas are full, long-lived Claude Code sessions with their own context: you can open one and talk to it directly, and they keep working across days."), a short demo GIF, and "What gets installed where".

|---|---|---|
| `cadre`, `cadre --tmux [--detach]`, `cadre ls`, `cadre attach`, `cadre stop`, `cadre help`, `cadre --version`, `cadre uninstall` | `init`, `use`, `migrate`, `up`, `project add\|link\|unlink\|sync\|trust\|path\|dir`, `allow [list\|add\|remove]`, `--check`, `ls --json` | `hook orchestrator`, `hook session`, `hook pre-push` |

**Old 0.1.x names** are not aliases. Each prints one line pointing to the new way and exits 1 (for example `cadre down` says "use cadre stop", `cadre add project` says "ask the orchestrator, or use cadre project add").

## 7. Security

- **Consent** comes only from the user in the orchestrator (3.1). Personas are refused for `allow add|remove`, `stop` with no name, `uninstall`, `migrate`, `init`, `use`, `project add|link|unlink|trust` (`CADRE_PERSONA` set).
- **Personas cannot change cadre's own files**: the fixed `Edit` denies and the `soft_deny` line (3.5), Claude Code's protection of `.claude` folders, `CADRE_HOME` pinning, and validation of the settings file before each launch.
- **No code from unexpected places**: `cadre.conf` is parsed, not run; configuration is read only from `~/.cadre` or `CADRE_HOME`.
- **Files that are not cadre's** (`~/.claude.json`, `~/.claude/settings.json`) are edited order-preserving, with a backup, atomically, and skipped on doubt.
- **Nothing is deleted**: unlinking keeps folders, migration moves old files aside, uninstall keeps cadres and projects.
- **No credentials in any cadre repository** (section 4).
- **Accounts**: cadre uses one Claude account at a time, whichever Claude Code is logged in with. Tools such as claude-swap can switch it; a switch applies to every cadre on the machine, and the cadre should be restarted afterwards (`cadre stop`, then `cadre`; conversations resume). Cadre has no dependency on claude-swap and no code from it.

## 8. Implementation

- **Go**, one static binary (`CGO_ENABLED=0`), module at the repository root (`cmd/cadre`, `internal/...`), stdlib plus `golang.org/x/term` and `x/sys`. Skill, protocol, `orchestrator.md` and template are embedded and written out where needed (`~/.cadre/framework/` is rewritten when the binary's version changes).
- **Runtime boundary**: all Claude Code specifics (flags, settings format, hook names, trust file, skill location) live in `internal/runtime/claude`; a source-scan test keeps them out of the rest. `internal/runtime/fake` exists for tests. There are no user-facing runtime options, and no further adapter work is planned.
- **Packaging**: goreleaser for macOS and Linux, arm64 and amd64, with `checksums.txt`; the tap formula installs the release binary (no bottles). Windows is unsupported (no tmux).
- **Testing**: Go unit tests (table-driven for the allow checker, from every review's regression lists) with `-race` on macOS and Linux; `tests/smoke.sh` runs end to end against the binary and is the parity contract. The bash implementation retires at parity.

## 9. Upgrading from 0.1.x

0.2.0 is a **breaking upgrade**. The CHANGELOG and README say so plainly and give the steps: stop your teams; `brew install rafi-ramdhani/cadre/cadre`; run `cadre`, which offers the one-time migration (3.7) and the switch of the skill link and hook; start teams again as you need them.

| Change | What to know |
|---|---|
| Cadre is a program, not a git clone | `git pull` in `projects/cadre` no longer upgrades (see the pending bridge, 11.1) |
| The cadre moves to `~/.cadre/<name>` | projects stay where they are; old files are kept in `cadre-before-0.2/` |
| Old command names | each prints a one-line pointer to the new way |
| `cadre ls` output | a new status screen; scripts use `cadre ls --json` |
| `cadre.conf` | read as `KEY=VALUE` only; shell code in it is ignored with a warning |
| Session names | gain the cadre name; running 0.1.x sessions show as legacy until restarted |
| The hook | becomes `<binary> hook orchestrator`; the first run offers to replace it |
| Python, jq | no longer needed |

## 10. Decisions and rejected options

- **Removed during planning**: per-cadre Claude accounts (one account at a time; see section 7); context-usage reminders and `cadre compact` (one skill line instead); user-facing runtime selection (`.runtime`, `RUNTIME`, `ORCHESTRATOR_RUNTIME`); `cadre update` (Homebrew upgrades); 0.1.x command aliases; `project export` and `project move` (projects are linked where they live); outside-`~/.cadre` cadres; usage-based account switching.
- **Parallel accounts, tested and dropped (2026-10-09)**: running different personas on different Claude accounts through separate `CLAUDE_CONFIG_DIR` folders was tested. A `SendMessage` to the other session's `uds:/tmp/cc-socks/<pid>.sock` address was delivered and woke it, but the receiving Opus 5.5 session's reply was stopped by safeguards twice (the second time in category [cyber]). Dropped as not dependable.
- **Multi-CLI**: a goal for later, behind the internal boundary; any future second CLI needs a messaging path shared with the orchestrator (a cadre MCP server was the noted route) and must enforce the fixed denies, or it is refused.

## 11. Pending decisions

1. **The 0.1.x bridge** (recommended: keep two tiny files on `main`). Without them, a 0.1.x user who runs `git pull` in their `projects/cadre` clone after the rewrite merges gets a broken `cadre` and, worse, a failing SessionStart hook in **every** Claude Code session. Recommendation: keep `bin/orchestrator-hook.sh` as a POSIX `sh` file that always exits 0 and prints nothing (or one valid notice), and `bin/cadre` printing one line: "cadre 0.2.0 is a new program: brew install rafi-ramdhani/cadre/cadre". The earlier pass-through and install offer are dropped.
2. **install.sh** for machines without Homebrew: keep a minimal downloader (fetch the release binary, verify its checksum, place it in `~/.local/bin`), with "run it again to upgrade"? Recommendation: keep it minimal; Homebrew is the documented path.
3. **`teams/` in backups**: team folders hold persona work. Recommendation: ignore `teams/` in the cadre's git (outputs can be large or sensitive) and keep a README there; the user can ask the orchestrator to track a file.
